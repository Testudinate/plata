## Трек A. Довести сдачу (блокирующее, 1–2 дня)

1. **Английская версия ответа.** Задание требует сдачу на английском
   (`Test Assignment ... .ru.md`, раздел «Формат»), в репозитории только
   `answer/test-assignment-answer-ru.{html,pdf}`, и `answer/README.md` это
   честно фиксирует. Пока её нет, всё остальное не имеет значения: работа
   формально не сдана. Перевод — не построчный: русская версия местами
   плотнее, чем нужно рецензенту, целевой объём задания — 5–8 страниц,
   сейчас 9.
2. **Ревизия приложений (`answer/source-review/`) — отдельным приложением к
   сдаче, а не основным документом.** 20 находок в материалах заказчика —
   сильный аргумент, но в основном тексте он смещает фокус с «что я построю»
   на «что у вас сломано».
3. **Один слайд-верхушка** (или первая страница) с картинкой: три числа COR за
   апрель → мост → канон. Это единственная вещь, которую рецензент запомнит
   через неделю.

## Трек B. Plata Risk Copilot — докер на VPS + Telegram

Идея из вопроса: отдельный стек на VPS, доступ через Telegram, знания — метаданные
из git плюс данные в Snowflake. Она правильная, и вот почему сильнее, чем кажется:
это не «ещё одна демка», а **исполняемое доказательство Part 4**. Утверждение
«инфраструктура готова к LLM-агентам» проверяется не документом, а живым ботом,
которому рецензент задаёт свой вопрос и получает число, совпадающее с каноном,
плюс SQL, плюс ссылку на контракт метрики.

### B.1 Архитектура

```
Telegram (allowlist chat_id)                     Claude Code / Desktop
        │                                                │
        ▼                                                ▼
plata-copilot-bot (aiogram)                     plata-copilot-mcp :8771
        │  HTTP, X-API-Key                                │
        └────────────────► plata-copilot-api :8770 ◄──────┘
                                    │
        ┌───────────────────────────┼────────────────────────────┐
        ▼                           ▼                            ▼
  pgvector (docs)          Snowflake (LLM_AGENT_RO)        Langfuse (self-hosted)
  приложения A–I,          RISK_GOV.AGENT.*                трейс: retrieve → plan →
  ответ, source-review,    V_COR_CANONICAL, SV_COR         sql → execute → validate
  PLAN/INVENTORY           витрины DM и TABLEAU            стоимость в USD
```

Один стек `docker-compose`, порты только на loopback, наружу — ngrok или TLS
(правила периметра ровно те же, что в hermes-memory). Сеть `llm-shared` —
общая с hermes-memory, чтобы расход токенов уходил в существующий `/usage`
и не заводить второй учёт.

### B.2 Конвейер ответа

Ключевое отличие от «бота с доступом к базе»: **модель не сочиняет формулу и
не угадывает таблицу**, а собирает ответ из контракта.

1. `docs_search` — pgvector по приложениям и материалам ответа (гибридный поиск
   с RRF и rerank уже написан в hermes-memory, переиспользуется как есть).
2. `context_get` — весь контекст-слой одним запросом (`AGENT.V_AGENT_CONTEXT`,
   ~3.4k токенов, помещается в системный промпт целиком).
3. Планирование: если вопрос про метрику из `METRIC_CONTRACTS` — берём формулу
   оттуда или спрашиваем `SEMANTIC_VIEW(SV_COR)`; сочинять агрегат запрещено.
4. `sql_run` — только `SELECT`, обязательный `LIMIT`, `QUERY_TAG` с id вопроса,
   пользователя и поверхности, таймаут на уровне пользователя Snowflake.
5. `pitfall_check` — по сгенерированному SQL прогоняются `PITFALLS.DETECTION_SQL`
   релевантных граблей. Не «модель предупредили» — а «ответ проверен».
6. Ответ в Telegram: число, единица, период, фильтры, использованный SQL,
   имя контракта метрики и её версия. Без SQL в ответе агент неотличим от
   генератора правдоподобных чисел.

Инструменты сверх этого: `freshness_check` (SLA и `ETL_LOG`),
`impact_analysis` (`META.V_CHANGE_IMPACT` — «что сломается, если поменять
объект X», прямой ответ на Part 3), `reconciliation` (`DQ.V_COR_RECONCILIATION`
— «почему у Finance другое число»).

### B.4 Контракт безопасности (не смягчать)

- **Отдельный сервисный пользователь** `PLATA_COPILOT_SVC`, key-pair
  аутентификация (не пароль), `DEFAULT_ROLE = LLM_AGENT_RO`,
  `DEFAULT_SECONDARY_ROLES = ()`. Сегодня у роли нулевой набор пользователей —
  первым делом закрывается именно это.
- **Network policy** на IP VPS. Ключ, утёкший из контейнера, вне этого IP
  бесполезен.
- **Свой warehouse** `WH_COPILOT` (XSMALL, auto-suspend 60 с) со **своим**
  resource monitor. Вопрос «сколько стоит агент» обязан иметь ответ, отделённый
  от стоимости пересборки песочницы.
- **Fail-closed по секретам**: сервис не стартует без ключа Snowflake, без
  API-ключа и без allowlist. Дефолтных значений не заводить.
- **Только чтение — правами, а не промптом.** Никакого `USE ROLE` в сессии,
  никаких временных грантов «на демо».
- **Allowlist `chat_id`** в Telegram; любой другой чат получает отказ и запись
  в лог. Бот в Telegram — публичная поверхность: без allowlist доступ к
  риск-данным получает любой, кто узнал имя бота.
- **`QUERY_TAG`** связывает вопрос из чата с `query_id`, поэтому
  `AGENT.V_AGENT_QUERY_AUDIT` становится персонифицированным: видно не только
  «агент спросил», а «кто попросил». Оговорка из ответа сохраняется:
  `ACCOUNT_USAGE` отстаёт до 45 минут — это аудит, а не контроль.

### B.5 Как измеряем, что агенту можно верить

Расширяем `AGENT.EVAL_QUESTIONS` с 16 до 40–60 вопросов, сохраняя пропорцию
поведенческих (отказ по PII, редирект с дропнутой таблицы, «посчитай по
формуле Finance» → канон плюс объяснение расхождения). Прогон — ночной, из
cron-контейнера, по образцу `eval_weekly.py`:

| Метрика | Смысл |
|---------|-------|
| accuracy@tolerance | доля числовых ответов в пределах `TOLERANCE` |
| table_precision | доля вопросов с правильно выбранным объектом |
| pitfall_rate | доля ответов, на которых сработал `DETECTION_SQL` (целевое 0) |
| refusal_correctness | поведенческие вопросы: отказал там, где надо, и не отказал там, где не надо |
| p95_latency, cost_per_question | кредиты Snowflake плюс токены модели |

Разбивка по `DIFFICULTY` обязательна: общая точность упирается в потолок на
лёгких вопросах и скрывает провал на hard — ровно та же ловушка, что уже
поймана в `eval_retrieval.py` через поле `kind`. Деградация валит прогон
(exit 2) и шлёт алерт.

## Трек C. Инженерные усиления песочницы

Отсортировано по отношению «вес в глазах рецензента / трудозатраты».

1. **dbt поверх фаз 5–6** (1.5–2 дня). JD называет dbt прямо: «мы используем
   dbt в проде, и слой трансформаций будет под вашим управлением». Сейчас это
   единственное явное требование вакансии, на которое в репозитории нет
   ответа. Дополнительная выгода не в самом dbt: `dbt tests` становятся частью
   DQ-контура, `exposures` — машинной версией `META.CONSUMER_REGISTRY`,
   `dbt docs` — вторым источником линиджа, независимым от `ACCOUNT_USAGE`.
2. **Детектор дрейфа, который реально работает** (0.5 дня). Part 2.5 описывает
   дизайн; `ALERT` + `TASK` в Snowflake превращают его в идущий процесс с
   уведомлением в тот же Telegram. Разница между «спроектирован» и «работает»
   — та же, что между ролью `LLM_AGENT_RO` и пользователем под ней.
3. **Git-репозиторий в Snowflake** (`CREATE GIT REPOSITORY` +
   `EXECUTE IMMEDIATE FROM`, 0.5 дня). Пересборка песочницы прямо из этого
   репозитория — самый короткий аргумент в разговоре о change management:
   изменение объекта проходит через pull request, а не через окно Snowsight.
4. **Streamlit in Snowflake** (0.5 дня): DQ-скоркарта и мост COR как страница.
   Нужно ровно для одного — показать, что governance-слой потребляется не
   только SQL-запросом и не только агентом.
5. **Генерация семантического YAML из `META.METRIC_DEFINITIONS`** (0.5 дня).
   Сейчас канон живёт в двух местах — реестре и `SV_COR` — и держится
   утверждением S13. Генерация из одного источника убирает саму возможность
   разъехаться.
6. **Довести владение до 100% на tier1–tier2** (0.5 дня): 14 из 54 объектов —
   это то, что мешает каталогу называться Controlled, и это уже названо в
   разделе 4.4 ответа.

## Что сознательно не делаем

- **Не даём агенту право записи** ни под каким видом, включая «временно для
  демонстрации».
- **Не строим двусторонний синк git ↔ Snowflake.** Направление одно:
  репозиторий — источник, Snowflake — цель. Урок мержа свободного текста уже
  оплачен в другом проекте.
- **Не тащим PII в контур агента** и не строим для неё маскирование как
  «вторую линию, которой достаточно».
- **Не пишем свой веб-UI.** Telegram и MCP покрывают обе аудитории; третья
  поверхность добавит поддержку, но не аргумент.
- **Не покупаем каталог.** Каталог здесь — таблицы рядом с данными, их
  одинаково читают человек, дашборд и агент.
