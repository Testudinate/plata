# Миграция на паттерны DeepSeek Harness (dsh)

Источник — «DeepSeek Harness. Иллюстрированное руководство» (developer preview
0.1, редакция 3, 19.08.2026), подготовленное для Stan/Testudinate и написанное
под ЕГО ДРУГИЕ проекты (`hermes-memory`, `telegram-bot`, `brazilmama`, Hermes
Agent на VPS). Этот документ — не пересказ, а перенос: что из архитектуры dsh
применимо к `plata`, что нет и почему, в той же дисциплине, что уже задана
`docs/IMPROVEMENTS.md` (таблица B.3 «что взято из существующих проектов, а не
написано заново») — только на этот раз сверка идёт не с hermes-memory, а с dsh.

**Обозначения статуса те же, что в остальных доках репозитория:**

| | |
|---|---|
| ✅ | уже сделано, паттерн совпал сам собой |
| 🟡 | частично, есть конкретный шаг до полного совпадения |
| ⬜ | применимо, не сделано |
| ⛔ | решено не переносить, с обоснованием |

---

## TL;DR

`dsh` — это харнесс вокруг модели: bash, файлы, песочница, реестр
инструментов, который агент собирает себе сам на VPS. У `plata` агента с
таким харнессом нет и быть не должно — `RISK_COPILOT` живёт **внутри**
Snowflake (`SNOWFLAKE.CORTEX.DATA_AGENT_RUN`), у него нет bash-инструмента, а
`sql_exec` — не шелл, а `SELECT` под ролью `LLM_AGENT_RO`
(`agent-service/README.md:18-20`, `docs/IMPROVEMENTS.md:139`: «не даём агенту
право записи ни под каким видом»). Ставить `dsh` вокруг `RISK_COPILOT` значило
бы построить снаружи Snowflake ровно тот тулинг, отсутствие которого — часть
доказательства Part 4 вакансии.

Поэтому перенос — не «установить dsh», а «сверить архитектурные паттерны dsh
с тем, что уже стоит в `plata`, слой за слоем». Транспортируется тонкий слой
`agent-service` (`bot.py` / `api.py` / `copilot.py` / `tracing.py`) — он и
есть тот кусок, что структурно похож на харнесс без цикла агента, — и общие
принципы (Definition/Provider/Consumer, наблюдаемость до функциональности,
детерминированный контроль вместо диалога). Сам `dsh` как рантайм в проект не
идёт.

## 1. Карта — 14 слоёв dsh против того, что уже стоит в plata

| Слой dsh | Что в plata | Статус |
|---|---|---|
| Модель (душа агента, меняется ключом) | Модель оркестрации Cortex (`claude-opus-4-8` / `claude-4-sonnet`), governed `CORTEX_MODELS_ALLOWLIST` и `CORTEX_ENABLED_CROSS_REGION` на уровне аккаунта, а не строкой в конфиге агента | ✅ сильнее — governance, а не удобство |
| Реестр инструментов, Definition/Provider/Consumer (рецепт 5) | `cor_metrics` → `SEMANTIC_VIEW SV_COR`, `risk_docs` → `CORTEX SEARCH CS_RISK_DOCS`, `sql_exec` → `SELECT` под `LLM_AGENT_RO` — паттерн реализован нативно, ни строки кода вне Snowflake | ✅ совпадение 1:1, без переноса |
| Sandbox-провайдер для shell (рецепт 2) | Нет bash-инструмента у агента вообще; `sql_exec` — не шелл | ⛔ не переносить, см. §6 |
| Разрешения / policy-as-code, обрыв цепочки без диалога (рецепт 4) | Роль `LLM_AGENT_RO` (только чтение витрин) отделена от `COPILOT_WRITER` (только `INSERT`/`UPDATE` журнала), `CORTEX_CLIENT_READ_ONLY` на сессии — граница на уровне права, не перехвата события | 🟡 граница сильнее, но контроль детективный, не превентивный — см. §3 |
| Хранилище сессий, append-only лог → replay/fork (рецепт 3) | `AGENT_RUN_LOG` (Snowflake, структурные колонки) + best-effort трейс в Langfuse (`tracing.py`) + `export_log.py` для человека — три параллельных, не единый поток | ⬜ настоящий разрыв, не «не делаем» — см. §4 |
| Компактизация / скилы / секция правил в промпте | Контекст-слой — версионируемые данные (`TABLE_CARDS`, `METRIC_CONTRACTS`, глоссарий), собираются dbt, проверяются его тестами, не файл-скилы и не инъекция клиентом | ⛔ не переносить, свой вариант сильнее — `SNOWFLAKE_NATIVE_FIT.md` уже это фиксирует |
| LLM-провайдер с fallback 429/5xx (рецепт 1) | Один governed путь инференса | ⛔ не переносить, см. §6 |
| Три способа запуска (Web UI / headless / SDK) | Одна точка входа — `api.py`, к ней уже подключён Telegram (`bot.py`), в очереди MCP (`SNOWFLAKE_NATIVE_FIT.md` §6.3) | ✅ тот же принцип «Consumer не зависит от рантайма», только на уровень выше — HTTP API, а не инструмент модели (`api.py:5-6`) |
| Четыре режима (Standard/Code/Minimal/Creator) | Нет режимов — единственный governed read-контур | ⛔ не применимо |
| Trajectory (по источникам, кто что добавил) | `tracing.py` пишет вложенный `generation` с разбивкой инструментов и SQL, но это отдельный best-effort канал, не источник истины | 🟡 частично, тот же разрыв, что и хранилище сессий |

## 2. Пять рецептов dsh — что валидно для plata

| Рецепт | Вердикт | Почему |
|---|---|---|
| 1. Провайдер модели с fallback | ⛔ не переносить | Governed model allowlist и data residency (`CORTEX_ENABLED_CROSS_REGION`, актуально для CNBV) — это ограничение по смыслу, а не отказоустойчивость; multi-provider hopping (как в `telegram-bot/ai-service.js`) обошёл бы именно тот периметр, который `plata` демонстрирует как governance |
| 2. Песочница-провайдер вместо approval | ⛔ не переносить | Нечего песочнить: у агента нет bash, `sql_exec` — whitelisted `SELECT` |
| 3. Хранилище сессий в Postgres+pgvector | ⛔ буквально, ⬜ по духу | Векторный поиск уже сознательно отменён в пользу Cortex Search (`docs/IMPROVEMENTS.md:74`: «сознательно не берём... свой RRF не выигрывает ничего кроме контроля»). Но идея «искать среди прошлых прогонов» не закрыта — см. §4, решение через Cortex Search, не pgvector |
| 4. Политика вместо диалога | 🟡 частично сделано | `LLM_AGENT_RO`/`COPILOT_WRITER` — это и есть обрыв цепочки, только на уровне права БД, что по собственному правилу `hermes-memory/CLAUDE.md` («настоящая граница — права роли, а не обёртка сервера») сильнее любого плагина. Не хватает: превентивности на уровне SQL, см. §3 |
| 5. Свой инструмент поверх внутреннего API | ✅ уже сделано | `cor_metrics`/`risk_docs`/`sql_exec` — ровно эта дисциплина (схема до вызова, ключ не в контексте модели, вызов логируется), только оформлено через `CREATE AGENT ... TOOLS`, а не `ctx.tools.register`. Применить её же для нового инструмента из §4 |

## 3. Находка при чтении кода: детективный контроль, а не превентивный

`lint_sql()` в `agent-service/app/copilot.py:92-124` проверяет SQL, которое
агент **уже вернул** (`ask()` вызывает `lint_sql` после `DATA_AGENT_RUN`,
`copilot.py:144`), против обязательных фильтров `TABLE_CARDS.MANDATORY_FILTERS`.
Это находка о том, что ответ мог быть неполон — она видна пользователю и в
`eval_agent.py` (`lint_findings`), но она приходит **после** исполнения
запроса под `LLM_AGENT_RO`.

В терминах рецепта 4 dsh: политика-плагин обрывает цепочку **до** `next()`,
то есть до эффекта. `lint_sql` — зеркальная схема: детектор после факта.
Для `plata` это, скорее всего, осознанный и правильный выбор — роль
read-only, поэтому у пропущенного фильтра нет последствий страшнее «неполный
ответ в чате», а не утечки или порчи данных. Но выбор нигде явно не
проговорён: `agent-service/README.md` описывает `pitfall_check` как
«DETECTION_SQL из AGENT.PITFALLS по выданному SQL» так, будто это защита, а
`docs/IMPROVEMENTS.md:101` фиксирует, что на практике это «линт по карточкам
вместо pitfall_check» — то есть более слабый, детективный механизм тихо
заменил более сильный замысел.

**Действие:** одна строка в докстринге `lint_sql` или в README — «детективный
контроль, не превентивный; превентивная граница — право роли» — снимает риск,
что кто-то прочитает лог линта как гарантию, а не как находку постфактум.

## 4. Свежий взгляд: чего в dsh нет аналога, а стоило бы

Разрыв из §1 («хранилище сессий / Trajectory») — единственное место, где у
`plata` действительно нет эквивалента dsh, а не осознанный отказ. Три канала
сейчас не пересекаются: `AGENT_RUN_LOG` (структура, для SQL-запросов),
Langfuse-трейс (для разбора стоимости и токенов), `export_log.py`
(для человека). Ни один не отвечает на вопрос dsh-Trajectory: «спрашивали ли
уже что-то похожее, и что тогда ответили».

Буквальный перенос рецепта 3 (Postgres+pgvector) — шаг назад: `plata` уже
доказала, что не хочет собственный векторный слой рядом с данными
(`docs/IMPROVEMENTS.md:74`). Но у неё **уже есть** нужный примитив —
Cortex Search, обкатанный на 86 чанках `risk_docs`
(`docs/SNOWFLAKE_NATIVE_FIT.md:37`). Тот же механизм, наведённый на
`AGENT_RUN_LOG.QUESTION` / `AGENT_RUN_LOG.RESPONSE`, даёт дух Trajectory без
единой новой компоненты и без выхода данных за периметр:

```
CORTEX SEARCH SERVICE CS_AGENT_RUNS
  ON AGENT_RUN_LOG(question, response)
  TARGET_LAG '1 day'   -- тот же TASK, что уже в очереди для ночного dbt
```

Дальше — четвёртый инструмент агента `similar_past_runs`, зарегистрированный
той же дисциплиной, что и `cor_metrics`/`risk_docs`/`sql_exec` (рецепт 5,
§2). Что это даёт:

1. Повторяющиеся вопросы отвечаются быстрее и с меньшим числом шагов —
   прямое снижение стоимости, которую сейчас видно в Langfuse ($0.31 на
   вопрос, `docs/SNOWFLAKE_NATIVE_FIT.md:115`).
2. Естественное расширение `eval_agent.py`: регресс сможет спрашивать не
   только «совпало ли число с ожиданием», но и «разошёлся ли новый ответ с
   семантически близким прошлым прогоном» — это тот же сигнал, ради которого
   в dsh есть `replay на другой модели`, только без буквального replay.

Это не в очереди ни `docs/IMPROVEMENTS.md`, ни `docs/SNOWFLAKE_NATIVE_FIT.md`
— то есть ровно то новое, что сверка с dsh добавляет поверх уже принятых
решений. Делать после того, как снят baseline (следующий пункт) — иначе
сравнивать эффект от нового инструмента будет не с чем.

## 5. Что переносить дословно — дисциплина, не код

| Принцип dsh | Где в plata уже применяется / должен |
|---|---|
| «Наблюдаемость до функциональности» (порядок фаз дорожной карты dsh) | Уже соблюдено на практике: трейсинг ✅ стоит раньше ставки стоимости ⬜, лог прогонов ✅ раньше жёсткой политики. Применить и к §4: сначала подключить `CS_AGENT_RUNS` только на чтение/просмотр, потом — как инструмент агента |
| Бенчмарк модели в Minimal mode («разница = вклад модели, а не обвязки») | Прямое совпадение с уже открытым пунктом `docs/IMPROVEMENTS.md` («Приоритеты» №2: «снять baseline регресса» — без него `eval_agent.py --compare` не с чем сравнивать). Сверка с dsh не добавляет работы — подтверждает, что это правильный первый шаг, не второстепенный |
| Рецепт 5 целиком (валидация до вызова, ключ не в контексте модели, вызов логируется) | Применить к `similar_past_runs` из §4 так же, как уже применено к трём существующим инструментам |

## 6. Явно не переносить

| Паттерн dsh | Почему не для plata |
|---|---|
| Sandbox-провайдер для bash (рецепт 2) | У `RISK_COPILOT` нет bash-инструмента и не будет — `docs/IMPROVEMENTS.md:139`: «не даём агенту право записи ни под каким видом, включая "временно для демонстрации"» |
| LLM-провайдер с fallback (рецепт 1) | Сломал бы governed model allowlist и резидентность инференса — это решение владельца данных (`docs/SNOWFLAKE_NATIVE_FIT.md` §6.2), не техническая настройка отказоустойчивости |
| pgvector как хранилище (рецепт 3, буквально) | Уже отменено решением, не долгом (`docs/IMPROVEMENTS.md:74`); дух рецепта закрывается иначе, см. §4 |
| Skills-каталог / инъекция промпта плагином | Контекст-слой `plata` — версионируемые данные под dbt-тестами, что сильнее файлового каталога скилов: расхождение канона ловится тестом `not_null`, а не полагается на то, что кто-то не забыл обновить файл |
| Четыре режима запуска и три способа запуска целиком | Не применимо — нет режимов у read-only governed контура; единственная точка входа уже есть (`api.py`) и уже обслуживает несколько поверхностей |
| Свой MCP+OAuth-шим один-в-один из `hermes-memory` | Штатный MCP-сервер аккаунта Snowflake уже есть и им же собрана вся песочница (`docs/SNOWFLAKE_NATIVE_FIT.md:38`) — своя OAuth-обвязка добавила бы поверхность без выгоды |

## 7. Чек-лист действий

   `docs/IMPROVEMENTS.md`, сверка с dsh (§5) только подтверждает порядок.
2. Одна строка в `copilot.py`/README: `lint_sql` — детективный контроль, не
   превентивный (§3).
3. После baseline — прототип `CS_AGENT_RUNS` + инструмент
   `similar_past_runs` (§4), той же дисциплиной, что три существующих
   инструмента (рецепт 5).
4. Ничего из §6 не внедрять — решения приняты, дублировать не нужно.
