## 2. Три параметра аккаунта, которые сами по себе являются governance-находкой

```sql
SHOW PARAMETERS LIKE 'CORTEX%' IN ACCOUNT;
```

| Параметр | Значение сейчас | Дефолт | Почему это важно |
|----------|-----------------|--------|------------------|
| `CORTEX_ENABLED_CROSS_REGION` | `ANY_REGION` | `DISABLED` | Промпт с риск-данными может уехать на инференс **в любой регион**. Для мексиканского финтеха под CNBV это не настройка производительности, а решение о резидентности данных — и оно сейчас принято по умолчанию в пользу удобства |
| `CORTEX_MODELS_ALLOWLIST` | `ALL` | `ALL` | Какие модели вообще допущены к риск-данным — не решено. Governance «какие модели можно» существует как параметр, но не как решение |
| `CORTEX_CODE_*_DAILY_EST_CREDIT_LIMIT_PER_USER` | `-1` (без лимита) | `-1` | Подушный лимит расхода на AI есть нативно и не включён |

Плюс два параметра, прямо усиливающих контракт безопасности агента:
`CORTEX_CLIENT_READ_ONLY` и `CORTEX_MCP_SERVER_FORCE_SQL_EXEC_READ_ONLY` —
аккаунт-уровневый запрет записи для клиентов и для MCP-сервера, поверх прав
роли. Обратите внимание на формулировку в описании первого: **cannot be
disabled once set**. Это ровно та граница, которую в ответе на Part 4 мы
описываем словами «ограничение правами, а не инструкцией», только ещё на
уровень ниже.

Это готовый абзац в ответ на Part 4 и на пункт вакансии про регуляторику
(CNBV, IFRS 9, Basel): «до того как агентам доверяют риск-данные, в аккаунте
принимаются три решения — резидентность инференса, список допущенных моделей,
лимит расхода на пользователя. Сегодня все три стоят в положении по умолчанию».

## 3. Соответствие пунктам вакансии

| Пункт JD | Нативный механизм | Вердикт |
|----------|-------------------|---------|
| «мы используем dbt в проде, слой трансформаций будет под вашим управлением» | **dbt Projects** + **Git repository** внутри Snowflake | **Брать.** Снимает необходимость внешнего оркестратора для демо: проект dbt живёт как объект аккаунта, версия берётся из этого репозитория. `dbt tests` становятся частью DQ-контура, `exposures` — машинной версией `META.CONSUMER_REGISTRY` |
| «SLA и observability витрин по измерениям DMBoK» | **Dynamic tables** (`target_lag` как декларативная свежесть), **DMF** `SNOWFLAKE.CORE.*`, **Alerts + Tasks** | **Брать.** `target_lag` превращает «своевременность» из метрики, которую мы считаем, в свойство, которое платформа обязана держать. Alerts закрывают разрыв «детектор дрейфа спроектирован, но не идёт» — их сейчас ноль |
| «полнота метаданных и lineage» | **Horizon Catalog**: теги, `ACCOUNT_USAGE.OBJECT_DEPENDENCIES`, Governance & security | **Брать с оговоркой.** Уже используется. Оговорка из ответа остаётся в силе: системная вью со ссылками на теги отстаёт до двух часов, поэтому живой каталог читает наши реестры, а теги держат политики и линидж |
| «контекстный слой для LLM, который агенты потребляют автономно» | **Cortex Analyst** поверх `SV_COR`, **Cortex Search** по приложениям, **Cortex Agents** (`AGENT_RUN`) | **Брать частично** — см. раздел 4 |
| «практический опыт с LLM/AI-агентами, что делает инфраструктуру пригодной для агентов» | **MCP-сервер Snowflake** (`CLAUDE_SQL` уже существует) + `CORTEX_MCP_SERVER_FORCE_SQL_EXEC_READ_ONLY` | **Брать.** Агентский доступ к хранилищу здесь уже нативный: этим сервером пользуется текущая сессия. Аргумент в разговоре сильный — не «я умею подключать агентов», а «агент, которым собрана эта песочница, ходил через штатный MCP аккаунта» |
| «регуляторные требования (CNBV, IFRS 9, Basel)» | `CORTEX_ENABLED_CROSS_REGION`, `CORTEX_MODELS_ALLOWLIST`, `AI_REDACT`, маскирующие политики | **Брать.** См. раздел 2 |
| «документирование схем, бизнес-понятий, паттернов запросов и подводных камней (Git-based, wiki или гибрид)» | **Git repository** в Snowflake + `COMMENT` + наши реестры | **Брать.** Гибрид, которого просит вакансия, здесь получается буквально: источник — git, витрина — таблицы рядом с данными |
| «Airflow или аналогичные оркестраторы» (плюсом) | **Tasks** и графы задач | **Достаточно.** Отдельный Airflow ради песочницы не нужен |
| «переиспользуемые паттерны для новых стран» | Git-репозиторий как источник сборки + теги + роли | **Брать.** Развёртывание нового рынка = прогон тех же скриптов из репозитория под другой префикс баз |

Отдельно про **AI Functions**, которых мы вообще не касались, а зря:

- `AI_PARSE_DOCUMENT` + `AI_EXTRACT` — приложения A–I в PDF и Markdown
  превращаются в карточки таблиц не руками. Это прямой ответ на «как вы
  масштабируете контекстный слой с 9 объектов до 40+ таблиц из вакансии».
- `AI_REDACT` — вторая линия по PII там, где маскирующей политики
  недостаточно (свободный текст в комментариях и логах агента).
- `AI_FILTER` / `AI_CLASSIFY` — классификация объектов по чувствительности и
  доменам при первичной разметке 54 объектов.
- `AI_EMBED_768` + `VECTOR_COSINE_SIMILARITY` — семантический поиск по
  документации **внутри** хранилища, без отдельной векторной базы.

## 4. Что это меняет в плане агента (трек B из IMPROVEMENTS.md)

Изначальный план предполагал pgvector на VPS для поиска по приложениям и свою
оркестрацию целиком. Проверка меняет две вещи.

**Отдаём Snowflake то, что он делает лучше:**

- Поиск по документации — **Cortex Search** вместо своего pgvector.
  Данные не покидают периметр, права наследуются от роли, индекс обновляется
  сам. Свой RRF плюс rerank из hermes-memory здесь не выигрывают ничего, кроме
  контроля, за который придётся платить поддержкой.
- Разрешение метрики — **Cortex Analyst** поверх `SV_COR`. Фильтр
  `statement_num >= 2` уже зашит внутрь агрегата, то есть вопрос на
  естественном языке физически не может получить разбавленную версию COR.
- Исполнение SQL — **штатный MCP-сервер** с
  `CORTEX_MCP_SERVER_FORCE_SQL_EXEC_READ_ONLY = true`, а не свой прокси.

**Оставляем себе то, чего в платформе нет или что нельзя отдавать вендору:**

- **Telegram и allowlist.** Шлюза в Snowflake нет.
- **Проверка ответа граблями** (`PITFALLS.DETECTION_SQL` после генерации SQL).
  Это наш инвариант, а не фича Cortex.
- **Регресс-набор и трейсинг.** Своя оценка правильности — это независимое
  свидетельство. Оценка агента инструментом того же вендора, которым агент
  сделан, слабее как аргумент; нативные Evaluations берём вторым мнением,
  когда до них дойдут права.
- **Учёт стоимости в USD** сквозь обе поверхности — уже написан в
  `hermes-memory/src/pricing.py`.

**Итоговая архитектура становится дешевле:** бот на VPS — тонкий клиент
(allowlist, форматирование, трейс, eval), тяжёлое — Cortex Search, Cortex
Analyst и MCP внутри Snowflake. Из трека B выпадают шаги B4 (pgvector) целиком
и половина B2; добавляется полдня на создание Cortex Search service и агента.
Оценка сокращается с 5–5.5 до **3.5–4 дней**, и, что важнее, ответ на вопрос
«почему у вас часть логики снаружи хранилища» становится коротким: снаружи —
только то, чего внутри нет.
