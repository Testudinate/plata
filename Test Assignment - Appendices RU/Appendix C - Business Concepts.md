## Соглашение о знаках (критично)

Разные таблицы используют разные знаки для колонок, связанных с COR. Ошибка здесь молча даёт неверный результат.

### Отрицательные (затраты) — challenger- и statement-таблицы

`cor_prnp`, `cor_1p_fact`, `cor_1p_predict`, `cor_collection_fact`, `cor` — все **отрицательные** в:
- `tableau.cor_challenger`
- `dm.stm_cc`, `dm.stm_cor_cc`

### Положительные (ожидаемые потери) — таблицы NPV Gen5

`cor_total_predict`, `bal_total_predict` — **положительные** в:
- `dm.npv_gen5_details`, `dm.npv_gen5_agg`

### Формула отклонения

```sql
-- Положительный результат = лучше прогноза (фактические потери < предсказанных)
cor_prnp + cor_total_predict AS deviation
```

Знаки взаимно сокращаются, потому что `cor_prnp` отрицательный (фактические затраты), а `cor_total_predict` положительный (предсказанные потери).

При джойне `stm_cor_cc` к `npv_gen5_details` для сравнения факта с прогнозом действует то же сокращение знаков. Соответствующий дашборд Tableau меняет знак `COR_TOTAL_PREDICT` (для stmt > 1), чтобы привести прогноз к отрицательному соглашению факта.

### Построение графиков

Когда факт и прогноз рисуются на одном графике, у NPV-прогноза нужно поменять знак:
```sql
-cor_total_predict AS forecast_cor  -- приводим к отрицательному соглашению факта
```
Предсказания challenger'а (`cor_1p_predict`, `cor_collection_predict`) уже отрицательные.

## Философия управленческого COR

В «идеальном» состоянии **весь** управленческий COR приходит только из двух источников:

1. **Inflow**: счета, мигрирующие из 0 в 1+ DPD
2. **Рост портфеля**: новые счета с 0 DPD, входящие в портфель

Любой ненулевой `cor_collection_fact` означает, что коллекшн отрабатывает хуже ожиданий модели. Это ключевой диагностический сигнал эффективности коллекшена.

## Соглашения по резервам в бизнес-плане (MxGAAP)

Текущий BP моделирует резервы MxGAAP только как **ставка × баланс основного долга** по 13 бакетам DPD (30, 60, ..., 390). Ключевые соглашения:

1. **Ставки применяются только к основному долгу.** Резервы по процентам (yield) не входят в запас резервов BP. BP отражает yield COR отдельной строкой потока во вкладках экономики, а не как ставка × баланс.

2. **Чтобы сравнить фактические резервы с BP на уровне бакета DPD**, используйте только резервы и списания по основному долгу:
   - On-BS: `PROVISIONS` × (`BALANCE_MXGAAP` / `EAD`) из `risk_prov.prov.MXGAAP_PROV_CC` (выводит резерв по основному долгу из общего резерва и доли баланса)
   - Off-BS: накопленные списания (WO) по основному долгу (из запроса детекции WO)
   - **Исключить**: резервы по процентам и списания процентов
   - Подразумеваемая ставка = `(prov_prnp + wo_principal) / balance_prnp` — должна близко совпадать со ставками BP.

3. **Механика WO на конец квартала:** BP моделирует списания, разгоняя ставку резервирования до 100% по поздним бакетам DPD на конец квартала. В фактических данных счета после этого убираются с баланса. Чтобы реконструировать «полный запас резервов по основному долгу», сопоставимый с BP, прибавьте накопленные списания основного долга обратно к балансовым резервам по основному долгу.

4. **Периметр продуктов:** «CC» в BP включает GRZD_CLIPPED. В Snowflake CC и GRZD_CLIPPED — отдельные значения `PRODUCT_RISKS`. При сверке фильтруйте соответственно.

## Gen3 COR: витрина выписок против снапшота портфеля

Два способа получить Gen3 COR на уровне выписки, фиксирующие разные моменты времени:

1. **Витрина выписок** (`stm_cor_cc.cor_prnp`): резерв Gen3 по выписке **на текущую дату расчёта** (сегодня). Непрерывно обновляется по мере движения счёта по просрочке. Включает и первоначальный inflow COR, и всю последующую работу коллекшена. Это взгляд «COR на сейчас».

2. **Снапшот портфеля** (`portfolio_cor.provisions_prnp_gen3` при `report_date = end_date AND dlq_first_dt = end_date`): запас резервов Gen3 **ровно в тот день, когда счёт ушёл в 1+ DPD**. Заморожен на эту дату, отражает только первоначальный скачок резерва, до какой-либо работы коллекшена.

**Связь**: `cor_prnp` (на сейчас) ≈ `provisions_prnp_gen3` в момент DPD1 + последующие изменения COR от коллекшена. Для недавно просроченных счетов значения будут близки. Для старых просрочек `cor_prnp` уйдёт в сторону в зависимости от результатов коллекшена.

**Паттерн Tableau**: используйте №2 как «COR на входе (inflow)», а №1 как «COR на сейчас». Разница изолирует эффект коллекшена. Оба — Gen3.

**Джойн для подхода №2**:
```sql
SELECT a.account_id, a.statement_num,
       b.provisions_prnp_gen3 AS cor_at_inflow
FROM risk_dm.dm.stm_cor_cc a
JOIN risk_dm.dm.portfolio_cor b
  ON b.account_id = a.account_id
  AND b.report_date = a.end_date
  AND b.dlq_first_dt = a.end_date
WHERE a.dpd1_flg = 1
```

## Жизненный цикл винтажа (CC)

Как COR% меняется на протяжении жизни винтажа:

- **Выписка 1**: COR% = 0 (ни одна дата платежа ещё не прошла — просрочка невозможна)
- **Ранние выписки**: COR% растёт по мере вызревания винтажа и первых пропущенных платежей
- **Середина жизни**: включаются прогоны CLIP, абсолютный COR растёт, но COR% часто снижается за счёт роста балансов
- **Зрелый винтаж**: COR% стабилизируется

### Ловушка при агрегации COR%

При расчёте агрегированного COR% всегда фильтруйте `statement_num >= 2`. У выписки 1 COR нулевой (даты платежа ещё не было), что размывает отношение и делает винтаж искусственно здоровее.

Аннуализируйте через `* 12`. НЕ используйте взвешивание по дням — стандартное соглашение здесь месячная аннуализация.

```sql
-- Правильный COR% по винтажам
SELECT util_month,
       SUM(cor_prnp) / SUM(avg_balance_prnp_net) * 12 AS cor_pct_annualized
FROM dm.stm_cor_cc
WHERE statement_num >= 2
GROUP BY util_month
```
