# План создания песочницы в Snowflake

Последовательный план: воссоздать в Snowflake объекты, описанные в приложениях A–H
тестового задания, и надстроить над ними governance-слой, который и является ответом
на Parts 1–5.

Принцип: **сначала физика (объекты и данные), потом governance, потом контекст для агента.**
Обратный порядок не работает — нечем демонстрировать.

---

## Фаза 0. Предпосылки и решения (0.5 дня)

### 0.1 Блокер доступа

Роль MCP-сессии не может создавать базы, а `USE ROLE` в сессии запрещён. Отсюда два варианта:

**Вариант A (рекомендую) — настоящие базы.** Одноразово под `ACCOUNTADMIN` в Snowsight:

```sql
USE ROLE ACCOUNTADMIN;

CREATE DATABASE IF NOT EXISTS ODS;
CREATE DATABASE IF NOT EXISTS RISK_DM;
CREATE DATABASE IF NOT EXISTS RISK_PROV;
CREATE DATABASE IF NOT EXISTS RISK_LEGACY;
CREATE DATABASE IF NOT EXISTS RISK_RDS;
CREATE DATABASE IF NOT EXISTS CREDIT_PROD;
CREATE DATABASE IF NOT EXISTS COLLECTION_PROD;
CREATE DATABASE IF NOT EXISTS PAYMENTS_PROD;
CREATE DATABASE IF NOT EXISTS POS_PROD;
CREATE DATABASE IF NOT EXISTS RISK_GOV;   -- наш governance-слой, в приложениях его нет

GRANT OWNERSHIP ON DATABASE ODS             TO ROLE HERMES_MCP_ROLE COPY CURRENT GRANTS;
-- ... то же для остальных девяти

-- нужно для Фазы 8 (data metric functions):
GRANT EXECUTE DATA METRIC FUNCTION ON ACCOUNT TO ROLE HERMES_MCP_ROLE;
GRANT DATABASE ROLE SNOWFLAKE.DATA_QUALITY_MONITORING_VIEWER TO ROLE HERMES_MCP_ROLE;
```

Отдаём владение конкретными базами, а не `CREATE DATABASE ON ACCOUNT` — грант уже, отзывается
одной строкой, «слепой» власти над аккаунтом роль не получает.

**Вариант B (без админа) — эмуляция.** Всё внутри `HERMES_MCP`, схемы называются
`RISK_DM__DM`, `ODS__PF_ENGINE` и т.д. Работает прямо сейчас, но имена перестают
совпадать с документацией — а в Part 4 именно совпадение имён в доке и в БД является
предметом разговора. Годится как черновик, не годится как демо.

Решение принимается до начала Фазы 1; всё остальное от него не зависит (имена вынесены
в переменные скриптов).

### 0.2 Прочие решения фазы

- **Warehouse**: `COMPUTE_WH` XS, `AUTO_SUSPEND = 60`. Объёмы (см. 0.3) на XS собираются минуты.
- **Масштаб**: 4 800 счетов (3 000 CC, 600 GRZD_CLIPPED, 800 PL, 400 POS),
  история 2025-07-01 … 2026-06-30 (365 дней). Апрель 2026 — полный месяц внутри окна,
  это и есть «апрель» из Part 2.
- **Детерминизм**: никакого `RANDOM()`. Псевдослучайность — `ABS(HASH(account_id, day, 'salt')) % N`.
  Пересборка даёт побайтово те же данные; иначе цифры в отчёте разъедутся с цифрами в БД.
- **Единица исполнения**: MCP-инструмент принимает **один** SQL-стейтмент за вызов.
  Поэтому каждый скрипт — либо один DDL, либо анонимный блок:
  `EXECUTE IMMEDIATE $$ BEGIN ... END; $$`. Батчи через `;` работать не будут.
- **Где живёт код**: `snowflake-sandbox/sql/NN_*.sql` в этом репозитории, нумерация = порядок
  запуска. dbt не берём: JD его упоминает, но здесь он добавит слой абстракции поверх
  задачи, которая сама про DDL. Если нужно показать владение dbt — отдельным шагом
  переложить Фазы 5–6 в модели (см. «Опции» в конце).
- **Идемпотентность**: каждый скрипт начинается с `CREATE OR REPLACE` / `DROP IF EXISTS`.
  Полная пересборка — `00_teardown.sql` + прогон по порядку.

### 0.3 Ожидаемые объёмы

| Таблица | Строк | Примечание |
|---------|-------|-----------|
| `dm.portfolio_cor` | ~1.5 млн | 4 800 счетов × ~330 активных дней |
| `dm.portfolio_bs` | ~1.5 млн | тот же панельный костяк |
| `tableau.cor_challenger` | ~1.5 млн | тот же костяк, другая нарезка колонок |
| `dm.stm_cor_cc` | ~40 тыс. | 3 600 CC-счетов × ~11 статементов |
| `dm.npv_gen5_details` | ~120 тыс. | 40 тыс. × 3 снимка `report_month` |
| остальные | < 50 тыс. | |

Итого < 5 млн строк, единицы гигабайт с запасом внутри бесплатного/пробного лимита.

**Приёмка фазы**: `SELECT CURRENT_ROLE()`, `SHOW DATABASES` показывают ожидаемое;
пробный `CREATE TABLE` в каждой из баз проходит.

## Фаза 2. Референсный слой и календарь (0.5 дня)

Первым делом — потому что от календаря зависят и статементы, и SLA-мониторинг.

1. `ods.ref.HOLIDAYS` — точно по Appendix B: `KEY VARIANT`, `"DATE" DATE`, `TYPE`
   (`'WEEKEND'`/`'HOLIDAY'`), `__PROCESSED_DTTM`, `__STG_PROCESSED_DTTM`.
   Наполнение 2024-01-01 … 2027-12-31: все субботы/воскресенья + мексиканские праздники.
   Подвижные даты (Jueves/Viernes Santo) считаются алгоритмом Гаусса для Пасхи —
   зашивать руками нельзя, иначе календарь протухнет за пределами вписанных лет.
   Именно этой таблицей потом считаются рабочие дни месяца для run-rate (App B).
2. `risk_gov.meta.dim_date` — служебный спайн: дата, флаг рабочего дня, месяц, квартал,
   номер рабочего дня в месяце. Не из приложений, но без него генераторы Фазы 4 нечитаемы.
3. `risk_gov.meta.ref_product` — единственный справочник продуктов и **всех его алиасов**:
   `CC` = `TDC` (App E) = `account_type 'CC'` в tableau; `GRZD_CLIPPED` входит в «CC» по
   методике BP, но отдельное значение в Snowflake (App C). Это Reference Data Management
   в чистом виде — при этом задание прямо говорит, что RDM сейчас не приоритет;
   справочник делаем минимальный, ровно чтобы было на что сослаться в Part 5.3 («что
   сознательно не берём в 90 дней»).
4. `risk_gov.meta.ref_sign_convention` — таблица «таблица+колонка → знак → смысл».
   Наполняется из Appendix C. Позже (Фаза 8) по ней автоматически генерируется DQ-проверка
   знака: не документ, который читают, а данные, по которым проверяют.

**Приёмка**: в апреле 2026 по `HOLIDAYS` получается корректное число рабочих дней;
запрос-образец из Appendix B отрабатывает дословно.

## Фаза 3. Слой ODS (0.5 дня)

Источники. Колонок в приложениях мало — берём то, что названо, остальное минимально
достаточное, и помечаем в `INVENTORY.md` как домысел.

- `ods.user_mgmt.USER_DATA` — `CLIENT_ID`, `GENDER`, `BIRTHDAY`, `STATE`. Это PII —

- `ods.pf_engine.STATEMENTS` — `STATEMENT_ID` (INTEGER), `ACCOUNT_ID`, `STATEMENT_DTTM`

- `ods.pc_tariffs.TARIFFS_ACCOUNTS`, `ods.fx_rates.USDMXN`, `ods.pc_app.TRANSACTIONS`
  (с типом `SPEI_IN`), `ods.pf_loans.TRANCHES`, `ods.pf_gl.GL_ENTRY_SOURCES` —
  скелеты на 100–1000 строк. Нужны, чтобы карта схем не врала, а не для расчётов.

**Приёмка**: джойн `dm.* → ods.pc_kernel.ACCOUNT` по `account_id = ID` даёт 100% попаданий;
наивный джойн по `report_date = STATEMENT_DTTM::DATE` теряет часть строк (так и задумано).

## Фаза 4. Генератор портфеля — ядро (1.5–2 дня)

Самая содержательная фаза. Всё, что дальше, — проекции одного панельного набора
«счёт × день». Строится одним каскадом CTE, детерминированно от `HASH(account_id)`.

1. **Счета и винтажи**: 4 800 счетов, `utilization_date` распределена по 12 месяцам
   (винтажные когорты), продукт, стартовый лимит, поведенческий тип
   (`risk_beh_type`: transactor / revolver / delinquent-prone) — тип задаёт дальнейшую
   вероятность просрочки.
2. **Дневная панель**: спайн дат от `utilization_date` до конца окна × счёт.
   Баланс = функция от лимита, типа поведения и сезонности; `credit_limit` растёт
   в моменты CLIP.
3. **Марковская цепь просрочки**: состояния 0 → 1-30 → 31-60 → 61-90 → 90+ → WO.
   Переходные вероятности зависят от `risk_beh_type` и возраста винтажа (App C:
   «COR% растёт по мере вызревания, затем стабилизируется»). Отсюда `dpd`,
   `dlq_first_dt`, `dlq_balance`, `prev_dlq_days`.
   Всплеск инфлоу вокруг праздников (App B) — множитель вероятности на датах из `HOLIDAYS`.
4. **Резервы**: три параллельных потока провизий на один и тот же портфель —
   `provisions_prnp_gen2` (LGD-стиль, ставка от DPD-бакета),
   `provisions_prnp_gen3` (hazard-стиль, ставка от бакета и «свежести» эпизода),
   MxGAAP (13 бакетов 30…390, ставка × principal, разгон до 100% на квартальных WO — App C).
   Gen2 и Gen3 близки помесячно, но **не совпадают** — это источник расхождения в Part 2.
5. **COR как дельта провизий**: `cor_*` = −(изменение резерва за день), знак отрицательный.
   Разложение Gen3: инфлоу = дельта на счетах, где `prev_dlq_days = 0 AND dlq_days >= 1`;
   коллекшн = дельта на остальных просроченных. По построению `cor = cor_1p_fact +
   cor_collection_fact` — свойство S6 выполняется тождественно, а не подгонкой.
6. **CLIP**: часть счетов получает повышение лимита на 4–8 статементе;
   `bs_day > utilization_date + 100` (App D). Отдельная замороженная когорта
   (`is_clip_freeze = TRUE`) — контрольная группа для `tableau.clip_cor_vintage`.
7. **Калибровка под S5**: параметры подбираются так, чтобы за апрель 2026 получилось
   примерно (допуск ±1 п.п., точные значения фиксируются после первой сборки):
   - Risk Analytics (стейтмент, Gen3, ×12) ≈ **12.5%**
   - Portfolio Monitoring (дневной, Gen3, ×365) ≈ **13.8%**
   - Finance (дневной, Gen2, помесячно) ≈ **11.6%**

   Разрыв 12.5 → 13.8 обязан раскладываться на: зерно (стейтмент против дня),
   отсутствие фильтра `statement_num >= 2`, знаменатель (`avg_balance_prnp_net` против
   `net_balance_prnp` на дату), календарь (будни против всех дней), аннуализация.
   Разрыв 13.8 → 11.6 — поколение модели (Gen3 против Gen2).
   **Этот мост и есть ответ на Part 2**, поэтому калибровка — часть плана, а не побочный эффект.

**Приёмка**: три числа расходятся; мост между ними сходится с точностью до копеек;
доли DPD-бакетов и уровень COR% правдоподобны для мексиканского карточного портфеля
(проверяется глазами, не автоматически).

8. `dm.npv_gen5_agg` — агрегат по счёту, `*_lt` колонки; обе формулы EL LT из App G

9. `dm.npv_naive_details`, `dds.stm_fact_forecast` (предджойненная материализация из App D),

`NPV_GEN5_PV_DETAILS` **не создаём** — она дропнута (S10). Вместо неё в Фазе 8 появится

**Приёмка**: дословно выполняются запросы-образцы из App C (COR at inflow), App D
(actuals vs gen5v1, мост числитель/знаменатель), App G (EL LT двумя формулами).

## Фаза 8. Governance-слой (1.5 дня) — здесь начинается собственно ответ

### 8.1 Метаданные и каталог (DMBoK: Data Catalog / Metadata)

- `COMMENT` на каждой таблице и **каждой колонке** — генерируется из `INVENTORY.md`,
  не пишется руками: источник правды один, иначе дока и БД разъедутся к третьей неделе.
- Теги из Фазы 1 навешиваются на объекты: владелец, стюард, критичность, PII, SLA.
- `risk_gov.meta.v_object_catalog` — вью поверх `INFORMATION_SCHEMA` + `TAG_REFERENCES`:
  объект, зерно, владелец, SLA, свежесть, критичность, ссылка на документацию.
- `risk_gov.meta.v_lineage` — линидж из `SNOWFLAKE.ACCOUNT_USAGE.OBJECT_DEPENDENCIES`
  (для вью — автоматом) плюс ручные рёбра для таблиц, наполняемых процедурами.
- **Ключевое**: каталог — это *таблицы*, а не вики-страница. Их одинаково читают
  человек, дашборд и агент. Это и есть переход «частично внедрён → Controlled» из Part 4.

### 8.2 Канонический метрик-слой (Part 2)

- `risk_gov.meta.metric_definitions` — реестр метрик: `metric_id`, бизнес-определение,
  зерно, источник, формула SQL, аннуализация, владелец, версия, дата вступления в силу.
- `risk_dm.dm.v_cor_canonical` — **одна** каноническая витрина COR. Предлагаемый канон
  (обосновывается в ответе): стейтментное зерно, Gen3, `statement_num >= 2`, ×12,
  знаменатель `avg_balance_prnp_net`. Причина: зерно совпадает с событием, на котором
  метрика определена (цикл выставления счёта), а не с датой снимка.
- `risk_gov.dq.v_cor_reconciliation` — мост: каноническое значение → три ведомственных,
  с явным вкладом каждого расхождения. Три команды перестают спорить, потому что видят
  не два числа, а разложение разницы.
- Старые расчёты не удаляются, а переименовываются в `*_legacy_finance`, `*_legacy_daily`
  и помечаются `deprecated_since` — иначе миграция не состоится, люди просто продолжат
  считать по-своему в Excel.

### 8.3 Data Quality (Part 2, Part 5)

Три уровня, ровно по лестнице DQM:

1. **Basic → Defined**: DMF от Snowflake на критичных таблицах —
   `SNOWFLAKE.CORE.FRESHNESS` на `report_date`/`end_date`, `NULL_COUNT` на ключах,
   `DUPLICATE_COUNT` на `(account_id, report_date)`, `ROW_COUNT`,
   `REFERENTIAL_INTEGRITY_COUNT` на `dm.* → dm.accounts`.
   `DATA_METRIC_SCHEDULE` = раз в час; результаты в
   `SNOWFLAKE.LOCAL.DATA_QUALITY_MONITORING_RESULTS`.
2. **Defined → Controlled**: собственные DMF на *семантику*, а не на форму —
   проверка знака COR, аддитивности Gen3, «в `stm_*` нет выходных дат»,
   «на statement_num = 1 COR = 0», «покрытие прогнозом ≥ 80%».
   Это те проверки, которых стандартный инструментарий не даёт и которые ловят
   реальные инциденты из приложений.
3. **Controlled → Continuing improvement**: SLA-таблица с порогами и владельцем,
   алерт (Snowflake Alert → email/Telegram) при нарушении, `risk_gov.dq.v_scorecard`
   со «светофором» по семи измерениям DMBoK (freshness, completeness, accuracy,
   consistency, timeliness, validity, uniqueness) и тренд качества по неделям.
   Метрика зрелости — не «сколько проверок», а «доля инцидентов, найденных
   мониторингом раньше, чем пользователем».

Календарь при этом обязателен: SLA на `stm_*` считается в рабочих днях по
`ods.ref.HOLIDAYS`, иначе каждый понедельник — ложная тревога (App B, S3).

### 8.4 Change Management (Part 3)

- `risk_gov.meta.model_registry` — версии моделей: Gen5v0/Gen5v1-old/Gen5v1-new,
  дата пересчёта, затронутые винтажи, дельта EL LT, ссылка на валидацию.
- `risk_gov.meta.change_log` — журнал изменений объектов: что, когда, кем, ломающее ли,
  кто из потребителей затронут, статус уведомления.
- `risk_gov.meta.consumer_registry` — кто потребляет каждый объект: дашборд Tableau,
  месячная отчётность, LLM-агент. Без него «оценить влияние» = обзвонить всех.
- Демонстрация на S9: пересчёт Gen5v1 → impact-запрос показывает, какие винтажи
  и какие дашборды поедут → версионированная витрина (`v_npv_gen5_v1`, `v_npv_gen5_v2`)
  → окно параллельной работы → deprecation.
- Демонстрация на S10: дропнутая `PV_DETAILS` → вью-надгробие, которое падает
  с внятным текстом «table dropped in <дата>, use NPV_GEN5_DETAILS», а не с
  `object does not exist`.

### 8.5 Доступ

Роли из Фазы 1 получают гранты; masking policy на `USER_DATA` (пол, дата рождения)
для всех, кроме `RISK_ANALYST_RW`; `LLM_AGENT_RO` не видит ни `raw`, ни `dds`, ни PII.

## Фаза 9. Контекст-слой для LLM (1 день) — Part 4
